Bird's-eye view

  • A single-player tabletop RPG in the browser where an LLM plays Dungeon Master. React 19 + Vite, almost all plain JavaScript. No server of its own: the browser calls Gemini, OpenAI or xAI directly with the player's own keys and is deployed as static files on Firebase Hosting.
  • The engine owns truth; the LLM owns feeling. Every die is rolled client-side with crypto.getRandomValues; HP, XP, AC, inventory, quests and combat live in one reducer. The DM streams prose plus a trailing JSON event block that declares what happened; the engine validates, clamps and applies it. The DM never rolls and never does math.
  • One turn is one pipeline. Player text → memory retrieval → system prompt (a byte-stable cached prefix + live state) → provider stream → parse → detectors → applyEvents → reducer → a background Scribe pass that extracts durable memory. Combat swaps the free-form event block for a bounded combat_exchange intent that the engine resolves atomically.
  • Memory is layered so long campaigns fit the token budget and feel remembered. World facts, a journal summarizing pruned chat, story-memory callback cards, NPC dossiers, hero tells, and a Gemini-embedded vector store. The engine judges every write (dedupe, supersession, dormancy, retraction); the LLM only proposes.
  • A hidden living world. Private campaign "fronts" with clocks the player and the DM never see as a dossier; the engine leaks only symptoms, rumor, and one permission card per scene. Background "directors" (one-shot LLM calls keyed on session.pending* markers) grow it.

Invariants

  • The LLM never rolls and never mutates state. Dice come only from dice.ts; a requested roll's modifier is ignored for the hero; applyEvents drops every non-exchange event while combat is active; handleRequestedRolls refuses to run in combat.
  • The engine is the single source of truth; the prompt describes it. If the DM "should" do math, the client already does it. A feature is a JSON field → a normalizer in eventChannels.js → a reducer action → a prompt line saying the field exists.
  • Every DM-writable mechanical channel ships with a replay ledger (coin, purchases, sales, spells, rests, XP, item grants; combat uses exchangeId). The DM re-emitting an applied event on a later turn is a proven failure mode. Windows are measured in conversational distance.
  • Every LLM lane is a trust boundary. A reducer fed by any lane projects the payload to known keys and clamps every text it stores; engine-owned stamps can never arrive from a lane.
  • The prompt prefix is byte-stable. Live state never enters a prefix block; the response mode is the tail. Tests pin the split and each dynamic block's ceiling.
  • Persistence is by construction. serializeGameState strips three fields and keeps the rest; autosave fires on any persisted-field change; a new state field needs no wiring. Settings and API keys are device-local and never in a save.
  • Resolved is terminal for story cards and for fronts. LOAD_GAME keeps the live user and the device's settings; Continue never calls the DM.
  • Fronts are private. The player never sees them; the DM sees id and faction stubs and at most one permission or doom card per scene. Resolution is the one moment a title is revealed.
  • The world's timing is dice, its content is directors. Arc reasoning (an LLM) decides what and where; a crypto die decides when; the reducer re-validates every install.
  • Records are frank in content, clinical in register. Durable text is written in neutral vocabulary at full specificity; nothing established is quietly tidied away.

A combat round

Active combat never uses the free-form roll path. The DM emits a bounded combat_exchange intent; engine/combatExchange.js validates it against live state, rolls every die, and seals one plan; the reducer commits it atomically by exchangeId; a separate narration-only call reads the stored result and cannot change it. Phases are COMBAT_PHASES in engine/combatPredicates.js.

Hidden fronts and the living world

A front is a private campaign clock: a faction or force, a goal, a clock from 0 to full, derived portent stages, and authored portents. The player never sees one. The DM never sees one as a dossier either: it reads id-and-faction stubs, one permission card (or one doom card) per scene, and in-world symptoms. The engine owns every number and every timing die; LLM directors only propose content, and each reducer installer re-validates it.
